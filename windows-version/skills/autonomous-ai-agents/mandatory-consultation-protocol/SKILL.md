# 强制协作协议 — Mandatory Consultation Protocol

## 核心规则（非可选）

**当小黑遇到以下情况时，必须停止盲目尝试，转而找小黄（Claude.app）沟通：**

1. **同一个问题尝试2次以上仍未解决**
2. **不确定方案是否正确**
3. **需要在多个技术方案间做选择**
4. **部署/修改后验证失败，原因不明**
5. **任何"卡住"的状态——不知道下一步该做什么**

## 违反后果

- 如果小黑在上述情况下继续盲目尝试而不找小黄沟通，属于**执行错误**
- 用户可以随时指出"你为什么不找小黄讨论？"

## 执行流程

### Step 1: 识别问题
当遇到困难时，先用一句话总结问题：
- 现象是什么？
- 已经试了什么？
- 为什么没成功？

### Step 2: 通过小黄发送问题

**小黄有两种接入方式：**

#### 方式A：Claude CLI on Windows（当前配置）
通过GitHub仓库协作：
1. 在antoken仓库创建Issue描述问题
2. 小黄在Windows上看到Issue后回复
3. 或通过WeChat直接沟通

#### 方式B：Claude Desktop GUI（macOS本地）
使用 `xiaohuang-claude-desktop-gui` skill：
```
1. skill_view("xiaohuang-claude-desktop-gui") 加载GUI操作流程
2. 准备问题描述（中文，简洁，包含上下文）
3. 通过 send-to-xiaohuang.sh 发送
4. 等待回复（screencapture + OCR 或 Cmd+A+C）
```

### Step 3: 讨论方案
- 把小黄的回复和自己的判断对比
- 如果小黄的方案合理，采纳执行
- 如果有分歧，把两个方案都报告给阿戴决定

### Step 4: 执行并反馈
- 执行讨论后的方案
- 把结果告诉小黄，继续迭代

## 问题模板

发给小黄时使用以下格式：

```
【遇到问题】
任务：[当前在做什么]
现象：[出了什么问题]
已试：[已经尝试过的方法]
困惑：[卡在哪里，为什么]

请帮我想想：
1. 这个问题可能的原因是什么？
2. 你建议怎么解决？
3. 有没有我没想到的角度？
```

## 教训：为什么必须执行本协议

Studio v15b 修 bug 过程中，素材不结合问题反复修了 5+ 次仍未解决。根因分析：
1. **清理死代码时误删了核心函数** (uploadBase64ToUrl) — 应该在删除前 grep 引用链
2. **搞混了两个完全不同的概念** (SVG edge stroke vs CSS grid linear-gradient) — 应该先 console.log 确认
3. **不了解数据格式** (blob URL vs data URL) — 应该先读代码理解数据流
4. **没有充分验证就报告"已修复"** — 浏览器 daemon 不稳定不是跳过验证的理由

如果在第 2 次失败时就找小黄讨论，可以避免后续 3 次无意义的尝试。

## 什么时候不需要找小黄

- 简单的文件读写操作
- 明确知道怎么做的步骤（如SCP上传、Nginx reload）
- 已有skill覆盖的标准流程
- 阿戴明确指示了具体做法

## 与团队协作协议的关系

- `team-collaboration-protocol` 定义了三方角色分工（小黑统筹+小黄方案+小白猪编码）
- 本skill是对小黑的**行为约束**——在执行过程中遇到困难时，不要变成"独角戏"
- 小黑既然是统筹角色，就应该善用团队资源，不是什么都自己扛

## 强制触发关键词

当小黑在内部思考中出现以下念头时，必须触发本协议：
- "再试一次看看"（已经试过1次了）
- "换个方式试试"（不确定新方式是否正确）
- "可能是XX的问题"（在猜原因）
- "奇怪，为什么不行"（困惑状态）

→ 这些时刻，停止尝试，找小黄。
