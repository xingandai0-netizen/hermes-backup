# 对比修改规范

## 强制规则：修改前必须对比

**问题**：Agent 直接修改代码，不先对比 v1 和 v2 的差异，导致引入新 bug。

**正确做法**：
1. 先 `diff` v1 和 v2 的对应文件
2. 列出所有差异点
3. 逐个分析差异是否需要保留
4. 确认每个差异的处理方案
5. 然后才开始修改

**禁止**：
- 不对比就修改
- 只看部分差异就动手
- 假设 v2 已经正确

## 对比工具

```bash
# 对比两个文件
diff v1-file.tsx v2-file.tsx

# 对比目录
diff -r v1-dir/ v2-dir/

# 搜索特定函数
grep -n "functionName" file.tsx
```

## 对比检查清单

### 状态管理
- [ ] v1 用什么 store？（Zustand/Jotai/Redux）
- [ ] v2 用什么 store？
- [ ] 数据结构是否一致？
- [ ] 字段名称是否一致？

### API 调用
- [ ] 端点路径是否一致？
- [ ] 请求参数是否一致？
- [ ] 响应字段是否一致？
- [ ] 错误处理是否一致？

### 组件结构
- [ ] Props 接口是否一致？
- [ ] 事件处理是否一致？
- [ ] 样式是否一致？
- [ ] 生命周期是否一致？

### 导入路径
- [ ] 文件路径是否变化？
- [ ] 导入方式是否变化？
- [ ] 是否有新增/删除的导入？

## 案例：@ 引用 bug

**问题**：@ 引用显示硬编码默认值，不显示实际上游节点

**根因**：
1. v1 有 `assetType` 字段
2. v2 只有 `nodeType` 字段
3. `getUpstreamMentions` 检查 `assetType`
4. 所以找不到上游节点

**教训**：如果先对比 v1 和 v2 的节点数据结构，就能立即发现 `assetType` 缺失

## 案例：生成卡住

**问题**：图片生成后一直显示"生成中"

**根因**：
1. v1 后端返回 `url` 字段
2. v2 后端返回 `output_url` 字段
3. 前端检查 `pollData.url`
4. 所以永远找不到结果

**教训**：如果先对比 v1 和 v2 的 API 响应格式，就能立即发现字段名不同
